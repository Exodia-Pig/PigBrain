# Gradle 빌드 최적화 일반론

사내 안드로이드 프로젝트의 재빌드 시간을 평균 93%(최대 94.4%) 줄인 과정을 일반화한 방법론입니다.

**소개 및 안내**

이 글의 사례는 실제 운영 중인 안드로이드 프로젝트에서 진행한 빌드 최적화 작업을 바탕으로 합니다. 프로젝트를 특정하지 않기 위해 다음과 같이 표기합니다.

- 사내 프로젝트 → **프로젝트 G**
- 광고 미디에이션 SDK → **광고 SDK A** (관련 태스크명·플러그인 좌표는 가명으로 재구성)

본문의 재현 실험과 프로파일 리포트 캡처는 개인 사이드 프로젝트인 [ziine-android](https://github.com/Nexters/ziine-android)에서 수행하여, 누구나 같은 방법으로 검증할 수 있습니다.

## 들어가며 — 빌드 시간은 곧 개발 생산성이다

안드로이드 개발자는 하루에도 수십 번 빌드 버튼을 누릅니다. 한 번의 빌드에 2분이 걸린다면, 하루 30회 빌드 기준으로 매일 1시간을 기다림에 쓰는 셈입니다. 더 큰 문제는 이 대기 시간이 집중의 흐름(flow)을 끊는다는 것입니다.

프로젝트 G도 같은 문제를 겪고 있었습니다. 코드 한 줄을 바꾸고 다시 빌드하는 데 **2분 11초**. "원래 오래 걸리는 프로젝트"라는 체념이 팀에 퍼져 있었습니다.

그런데 정말 원래 그런 걸까요? 이 글은 그 질문에서 시작해, **어떤 Gradle 프로젝트에도 적용할 수 있는 빌드 최적화 방법론**을 정리한 것입니다. 핵심은 단순합니다.

1. **측정한다** — 어떤 태스크(Task)가 실제로 실행되고, 얼마나 걸리는지
2. **의심한다** — 그 태스크가 정말 필요한 작업인지
3. **제거한다** — 필요 없다면, 근거를 확보하고 걷어낸다


## 1. 측정 프레임: 3가지 빌드 시나리오

빌드 속도를 이야기할 때 "빌드가 느리다"는 말은 모호합니다. 개발 과정에서 마주치는 빌드는 성격이 다른 세 가지로 나뉘고, 각각 따로 측정해야 합니다.

| 시나리오                                               | 상황                                       | 개발자가 겪는 빈도           |
| ------------------------------------------------------ | ------------------------------------------ | ---------------------------- |
| **클린 빌드** / clean build                            | `clean` 직후 또는 브랜치 전환 후 전체 빌드 | 낮음 (하루 1~2회)            |
| **무변경 재빌드** / no-change build                    | 코드 변경 없이 다시 빌드                   | 중간                         |
| **코드 변경 후 재빌드(증분 빌드)** / incremental build | 파일 몇 개를 수정하고 다시 빌드            | **매우 높음 (하루 수십 회)** |

체감 생산성에 가장 크게 영향을 주는 것은 세 번째, **코드 변경 후 재빌드**입니다. 개선 효과를 판단할 때도 이 세 시나리오를 각각 측정해야 "클린 빌드는 빨라졌는데 증분 빌드는 그대로"인 함정을 피할 수 있습니다.

프로젝트 G의 최적화 전 초기 측정값은 다음과 같았습니다. (진단용 1회 측정값입니다. 6장의 최종 검증은 별도 PC 2대에서 10회 평균으로 다시 측정했기 때문에 절대값이 다르며, 그래서 이 글의 효과 비교는 개선율 기준입니다. "코드 변경"은 측정 편차를 없애기 위해 **로그 한 줄 추가**로 통일했습니다.)

| 시나리오            | 최적화 전 |
| ------------------- | --------- |
| 클린 빌드           | 4분 52초  |
| 무변경 재빌드       | 24초      |
| 코드 변경 후 재빌드 | 2분 11초  |

여기서 이상한 점이 두 가지 보입니다. **무변경인데 24초**가 걸리고, 코드 몇 줄 변경에 **2분 이상**이 걸립니다. Gradle의 증분 빌드(incremental build)가 제대로 동작한다면 나올 수 없는 숫자입니다. 이 "뭔가 이상하다"는 감각이 최적화의 출발점이었습니다.


## 2. 배경지식: Task Outcome — 어떤 태스크를 봐야 하는가

Gradle은 빌드할 때 수행하는 각 태스크의 실행 결과(task outcome)를 **라벨**로 남깁니다. 빌드 로그에서 태스크 이름 뒤에 붙는 그 표시입니다.

```text
> Task :app:compileDebugKotlin
> Task :app:mergeDebugResources UP-TO-DATE
> Task :app:processDebugJavaRes NO-SOURCE
> Task :app:lintDebug SKIPPED
```

| 상태            | 의미                                       | 실제 실행 여부 |
| --------------- | ------------------------------------------ | -------------- |
| `UP-TO-DATE`    | 입력/출력이 이전 빌드와 같아 결과를 재사용 | ❌              |
| `FROM-CACHE`    | 빌드 캐시(build cache)에서 출력을 복원     | ❌              |
| `NO-SOURCE`     | 처리할 입력 파일 자체가 없음               | ❌              |
| `SKIPPED`       | 조건(`onlyIf` 등)에 의해 제외됨            | ❌              |
| `Did No Work` * | 태스크에 진입했지만 실질적 작업 없이 종료  | ⚠️              |
| **(빈값)**      | **실제로 작업을 수행함**                   | ⭕              |

\* `Did No Work`는 빌드 로그에 찍히는 라벨은 아니고, 프로파일 리포트나 Build Scan에서 볼 수 있는 분류입니다.

<details>

<summary>Task Outcome 상세 설명</summary>

1️⃣ UP-TO-DATE  
이전 빌드 이후 태스크의 입력(Input)과 출력(Output)에 변경 사항이 없어, 이전 실행 결과를 그대로 재사용한다. 실행 시간이 거의 소요되지 않는다.

2️⃣ NO-SOURCE  
태스크가 처리해야 할 입력 파일 자체가 존재하지 않는 상태이다. 예를 들어, Java 리소스 처리 태스크인데 프로젝트에 Java 리소스 파일이 없는 경우가 이에 해당한다.

3️⃣ SKIPPED  
onlyIf 조건이 false를 반환하거나, 선행 태스크 실패 등의 이유로 태스크 실행 자체가 건너뛰어진 상태이다.

4️⃣ Did No Work  
태스크의 액션(Action) 코드는 실행되었으나, 내부 로직에서 실질적인 작업이 발생하지 않은 상태이다. 태스크에 진입하여 함수 호출과 조건 체크까지는 수행되지만, 컴파일이나 파일 처리 같은 무거운 작업은 수행되지 않아 실질적으로 빌드 시간에 영향을 주지 않는다. (UP-TO-DATE는 태스크 진입 전에 생략되는 반면, Did No Work는 진입 후 조기 종료되는 차이가 있다.)

🚨 (빈값) — 주의: 빌드 시간의 직접적 원인  
태스크가 실제로 작업을 수행한 상태이다. CPU와 I/O 리소스를 소모하며, 빌드 시간에 직접적인 영향을 미친다. 빌드 최적화 시 이 상태의 태스크들이 주요 분석 대상이 된다.

---
</details>

Gradle은 각 태스크의 입력(input)과 출력(output)을 추적해서, 입력이 변하지 않은 태스크는 이전 결과를 재사용합니다. 이것이 증분 빌드의 원리입니다.
(Gradle은 이전 빌드 시점의 입력/출력 상태를 캐싱, 다음 빌드 시 입력이 변경되지 않았다면, 이전 출력을 그대로 재사용)

여기서 최적화의 첫 번째 원칙이 나옵니다.

> **빌드 시간을 줄이려면, 상태가 (빈값)인 태스크 — 즉 실제로 실행된 태스크만 보면 된다.**

라벨이 붙은 태스크는 이미 Gradle이 알아서 건너뛰고 있으므로, CPU와 I/O를 소모하며 빌드 시간에 직접 기여하는 것은 (빈값) 태스크들입니다.
빌드 속도 병목을 분석할 때, 상태가 (빈값)인 태스크 = 실제 실행된 태스크를 중심으로 런타임을 확인하면 최적화 대상을 효과적으로 식별할 수 있습니다.
